# 《夜蚀 Nightfall》技术方案 v0.1

> 类型：单机 · 卡牌构筑 · Roguelike 爬塔
> 对标：《月圆之夜》(Night of the Full Moon)
> 引擎：Godot 4.5 stable
> 状态：战斗原型已可运行并通过规则回归测试

---

## 1. 项目定义

### 1.1 目标体验

一场 Run ≈ 30–45 分钟，玩家在分支地图上推进 10–12 层，通过「战斗 → 选牌 → 构筑」逐步成型，
在 Boss 战接受构筑强度检验。核心乐趣来自**卡组协同**（而非操作），因此系统设计的重心是：

1. 卡牌组合是否有足够多的可行流派；
2. 每层决策是否有真实取舍（血量 / 金币 / 卡位）；
3. 信息是否完整（敌方意图必须可读）。

### 1.2 本阶段目标

用户确认的路线是「先出技术方案与原型验证」。因此本阶段的交付不是完整游戏，而是：

- 一份可执行的技术方案（本文档）；
- 一个**真实可跑**的战斗原型，用来验证：
  - 引擎与工具链是否顺畅；
  - 战斗手感（出牌节奏、意图可读性、动画反馈）；
  - 数据驱动的内容管线是否好用；
  - 规则层能否被自动化测试覆盖。

### 1.3 验收标准（已达成）

| 项 | 标准 | 结果 |
| --- | --- | --- |
| 可运行 | 双击/命令行直接进入战斗 | ✅ |
| 规则正确 | 伤害、格挡、状态、抽洗牌、胜负 | ✅ 61 项断言通过 |
| 完整循环 | 三场连打 → 结算 → 推进 → 最终结算 | ✅ 自动演示通过 |
| 可扩展 | 加一张卡/一个敌人只改 JSON | ✅ |
| 无外部资源 | 工程内无图片/音频文件 | ✅ |

## 2. 引擎选型

### 2.1 候选对比

| 维度 | Godot 4.5 | Unity 6 | Cocos Creator 3.x | Unreal 5 |
| --- | --- | --- | --- | --- |
| 授权成本 | 完全免费、MIT | 免费版有收入门槛 | 免费 | 分成 5% |
| 2D / UI 能力 | 强（Control 体系原生） | 中（UGUI 够用） | 强（偏 H5） | 弱（UMG 重） |
| 包体 | 小（~40 MB 起） | 大（~60 MB 起） | 小 | 很大 |
| 移动端 | 支持（Android/iOS） | 成熟 | 强（微信小游戏） | 弱 |
| 文本工程化 | 全文本 `.tscn/.tres`，易 diff | 场景为 YAML，但依赖编辑器 | 场景 JSON | 二进制为主 |
| 热重载 | 脚本/场景可热重载 | 需插件 | 支持 | 有限 |
| 中国团队生态 | 少 | 最多（外包/教程） | 多（小游戏） | 少 |
| 本机可自动化验证 | **可以**（headless 跑逻辑） | 难（需编辑器许可证） | 可以 | 难 |

### 2.2 结论

选择 **Godot 4.5 + GL Compatibility 渲染后端**，理由：

1. **卡牌游戏是 UI 密集型 2D 项目**，Godot 的 Control/锚点/主题体系比 Unity 的 UGUI + Canvas 更轻；
2. **工程是纯文本**，卡牌数值、场景、脚本都能被 Git 精确 diff，适合长期内容迭代；
3. **可以在无头模式下跑完整逻辑**，这是本项目敢做自动化回归测试的前提；
4. 免费且无分成，对独立项目友好；
5. 若后期要上微信小游戏，可迁移 Cocos 或改用 Godot 的 Web 导出（需权衡包体与性能）。

> 若你的团队已有成熟 Unity 管线、或必须依赖 Asset Store 资源，改回 Unity 也完全可行——
> 关键在于本文档第 3 节的**分层**与第 7 节的**确定性**，这两点是引擎无关的。

### 2.3 渲染后端

使用 `gl_compatibility`（OpenGL 兼容模式）而非 Forward+：

- 2D 卡牌游戏不需要 PBR/SSAO；
- 兼容性最好（老显卡、移动端、Web 导出）；
- 功耗低，笔记本/手机续航友好。

## 3. 系统架构

### 3.1 分层

```
┌─────────────────────────────────────────────┐
│  流程层  RunManager (GameState)              │  局内进度、层数、回血、重开
├─────────────────────────────────────────────┤
│  表现层  BattleScreen / CardView / UnitView  │  只读状态 + 播放事件
│          PlayerView / ArenaBackground        │
├─────────────────────────────────────────────┤
│  规则层  BattleEngine                        │  ★ 纯逻辑，不 import 任何节点
├─────────────────────────────────────────────┤
│  数据层  DB (JSON → Dictionary)              │  卡牌 / 敌人 / 关卡表
└─────────────────────────────────────────────┘
```

依赖方向：**表现层 → 规则层 → 数据层**，规则层不反向依赖。这条约束是整个架构的地基：

- `BattleEngine` 继承 `RefCounted`，不碰 `Node`、不碰 `Timer`、不碰 `Input`；
- 因此它能被 `--headless --script` 直接实例化做单元测试；
- 也因此它将来能被搬到服务端做权威结算（若做 PVP）。

### 3.2 目录规范

```
Nightfall/
├─ data/                  # 内容数据，策划可直接改
│  ├─ cards.json
│  └─ enemies.json
├─ scripts/
│  ├─ core/battle_engine.gd      # 规则层，无 UI 依赖
│  ├─ data/database.gd           # autoload: DB
│  ├─ game_state.gd              # autoload: Game（Run 状态）
│  └─ ui/                        # 表现层
│     ├─ ui_theme.gd             # 颜色/字体/控件皮肤
│     ├─ battle_screen.gd        # 场景编排 + 事件动画
│     ├─ card_view.gd            # 卡面（_draw）
│     ├─ unit_view.gd            # 敌人（_draw）
│     ├─ player_view.gd          # 玩家面板 + 能量球（_draw）
│     └─ arena_bg.gd             # 程序化背景
├─ scenes/main.tscn       # 唯一场景
├─ tests/test_battle.gd   # 无头回归测试
└─ docs/技术方案.md
```

### 3.3 为什么用事件流

引擎的每个动作（出牌、受击、回合切换）都会向 `events` 数组追加一条记录，表现层通过
`take_events()` 取走并逐条播放动画。

好处：

1. **动画与逻辑解耦**：动画时长改到 0 也不影响规则；
2. **可回放**：`seed + 玩家操作序列` 可以完整重演一局（用于复现 bug、做战报）；
3. **可测试**：测试不需要等动画，直接断言数值；
4. **为联机预留**：将来若做 PVP，服务端发事件、客户端播动画，天然一致。

事件类型（当前）：

| 事件 | 触发 | 表现层反应 |
| --- | --- | --- |
| `turn_start` | 玩家回合开始 | 刷新回合数 |
| `draw` / `reshuffle` / `draw_fail` | 抽牌 | 更新牌堆计数 |
| `card_played` / `exhaust` | 出牌 | 移除手牌 |
| `damage` | 造成伤害 | 飘字、受击闪白、震屏 |
| `block` | 获得格挡 | 飘字「+N 格挡」 |
| `heal` | 治疗 | 绿色飘字 |
| `status` | 状态增减 | 状态药丸刷新 |
| `enemy_act` / `intent` | 敌人行动 / 意图推进 | 敌人头顶动作名、意图气泡 |
| `victory` / `defeat` | 结算 | 遮罩层 |

## 4. 数据模型

### 4.1 卡牌（`data/cards.json`）

```json
{
  "id": "poison_blade",
  "name": "毒刃",
  "cost": 1,
  "type": "attack",          // attack / skill / power
  "target": "enemy",         // enemy / none
  "rarity": "uncommon",      // starter / common / uncommon / rare
  "desc": "造成 5 点伤害，施加 3 层中毒。",
  "exhaust": false,          // 打出后消耗
  "effects": [
    { "k": "damage", "v": 5 },
    { "k": "status", "status": "poison", "v": 3 }
  ]
}
```

效果指令表：

| `k` | 参数 | 语义 |
| --- | --- | --- |
| `damage` | `v`, `hits` | 对目标造成 v 点伤害，可多段 |
| `block` | `v` | 自身获得格挡 |
| `draw` | `v` | 抽牌 |
| `energy` | `v` | 获得能量 |
| `heal` | `v` | 治疗 |
| `status` | `status`, `v` | 对目标施加状态 |
| `self_status` | `status`, `v` | 对自身施加状态 |

设计取舍：**用「效果指令数组」而不是表达式脚本**。优点是解析零成本、可被工具校验、可自动生成描述；
代价是复杂卡（条件、循环、动态数值）表达力不足。解决方式见 8.3：为复杂卡预留 `script` 字段，
由少量手写 `Effect` 资源处理，而不是让所有卡都变成代码。

### 4.2 敌人（`data/enemies.json`）

```json
{
  "id": "goblin",
  "name": "哥布林劫掠者",
  "hp": 40,
  "shape": "fang",           // 程序化剪影：fang / spike / eye
  "tint": "#7FA05A",
  "scale": 1.12,
  "moves": [
    { "name": "劈砍", "type": "attack", "damage": 8 },
    { "name": "磨刀", "type": "buff", "status": "strength", "value": 2 }
  ],
  "pattern": [0, 1, 0]
}
```

- `pattern` 是 `moves` 下标的循环序列，决定出招顺序；
- 意图在**回合开始时就确定并公开**，玩家据此决策——这是卡牌 Roguelike 的核心信息设计；
- `preview` 由引擎按当前力量/虚弱实时计算，玩家看到的数字永远是真值。

### 4.3 运行时单位

```gdscript
{
  id, name, hp, max_hp, block,
  statuses: { strength, vulnerable, weak, poison },
  is_player, alive,
  def,          # 敌人原始定义
  pattern_idx,  # 出招指针
  intent        # 当前意图（含 preview）
}
```

### 4.4 状态效果

| 状态 | 效果 | 衰减 |
| --- | --- | --- |
| 力量 strength | 每段攻击 +N | 不衰减 |
| 易伤 vulnerable | 受到伤害 ×1.5 | 回合末 -1 |
| 虚弱 weak | 造成伤害 ×0.75 | 回合末 -1 |
| 中毒 poison | 回合末损失 N 点生命（无视格挡），然后 -1 | 每回合 -1 |

## 5. 战斗规则

### 5.1 回合状态机

```
        ┌──────────────┐
        │  player 回合  │  能量重置、格挡清零、抽 5 张
        └──────┬───────┘
               │ 出牌 / 结束回合
        ┌──────▼───────┐
        │  敌人依次行动  │  每个敌人：格挡清零 → 执行意图 → 中毒结算 → 意图推进
        └──────┬───────┘
               │ 玩家未死且敌人未清空
        ┌──────▼───────┐
        │   回到 player  │
        └──────────────┘
```

胜利判定在**每次伤害结算后**触发（不必等回合结束），失败判定在玩家生命归零时触发。

### 5.2 伤害公式

```
基础值 = 卡牌/招式数值 + 攻击方力量
若攻击方虚弱： × 0.75
若受击方易伤： × 1.5
最终 = floor(结果)，且 ≥ 0
实际扣血 = 最终 - min(格挡, 最终)
```

全部整数运算 + `floor`，保证跨平台一致（浮点在不同平台可能产生 1 点误差，卡牌游戏里这是不可接受的）。

### 5.3 牌堆

- 抽牌堆空时，弃牌堆洗回抽牌堆（洗牌使用 `RandomNumberGenerator`，受 seed 控制）；
- 手牌上限 10；
- 出牌后进弃牌堆，`exhaust: true` 的牌进消耗堆，本场不再出现。

### 5.4 敌人意图

```gdscript
intent = moves[pattern[pattern_idx % pattern.size()]]
intent.preview = attack_value(enemy, intent.damage)   // 实时含力量/虚弱
```

表现层把 `preview` 直接画在气泡上。玩家不需要自己算。

## 6. 表现层

### 6.1 为什么原型用程序化绘制

原型阶段没有美术资源，用 `_draw()` 画出卡框、费用球、敌人剪影、血条、意图气泡、背景光晕：

- 零资源依赖，改一行代码就换配色；
- 每张卡/每个敌人只占一个 `Control`，性能无忧；
- 方便快速验证**布局**与**信息层级**，而不是验证「好不好看」。

**正式版必须替换为美术资源**：卡面用 `TextureRect` + 九宫格边框，敌人用 `AnimatedSprite2D`，
届时 `CardView/UnitView` 的绘制函数整体替换，接口（`configure/emit`）保持不变。

### 6.2 事件 → 动画

```
engine.play_card() → events[] → _animate(events) → 逐条 await 计时器 → _refresh() 重建 UI
```

`_refresh()` 是「全量重绘」策略：每次动作后重读引擎状态并重建手牌、刷新血条。
对卡牌游戏（同屏节点 < 100）完全够用，且避免了大量增量同步的状态不一致 bug。

### 6.3 交互

- 单目标敌人时，点卡即出；
- 多目标时进入**选敌态**：敌人显示高亮环，点敌人确认，右键取消；
- 不可打出的卡（能量不足）整体降透明度，点击会抖动提示而非静默失败；
- 空格结束回合。

### 6.4 中文字体（踩过的坑）

Godot 默认字体不含 CJK；`SystemFont` 在 **headless 模式**下解析不到系统字体，
在 **Web 导出**里更是根本没有文件系统可读——两种情况都会渲染成方块。

最终方案：**字体文件随工程打包**（`assets/fonts/NotoSansSC-Regular.otf`，OFL 授权，7.9 MB），
`UITheme.cjk_font()` 优先 `load()` 内置字体，失败才按平台探测系统字体作为兜底：

| 平台 | 候选路径 |
| --- | --- |
| macOS | `PingFang.ttc` → `Hiragino Sans GB.ttc` → `STHeiti Medium.ttc` |
| Windows | `msyh.ttc` → `simhei.ttf` → `simsun.ttc` |
| Linux | Noto Sans CJK → 文泉驿 |

> 发布前应内置一份 OFL 授权字体（思源黑体 / Noto Sans SC），避免依赖用户系统字体。

### 6.5 分辨率

设计分辨率 1440×900，`stretch/mode = canvas_items`，`aspect = expand`。
所有布局用绝对坐标（因为画布尺寸被锁定），保证在不同窗口尺寸下等比缩放。

## 7. 确定性与可回放

- 每场战斗的种子 = `run_seed + encounter_index * 7919`，同一 Run 内每场种子固定；
- 所有随机（洗牌）只走 `BattleEngine.rng`，不使用全局 `randi()`；
- 因此「种子 + 操作序列」可完整重放一局。

这条设计现在看起来「没必要」，但它是三件事的前提：

1. **复现 bug**：玩家报「第三回合卡死」，给个种子就能复现；
2. **平衡测试**：跑一万局 AI 对战，统计各流派胜率；
3. **PVP / 排行榜**：服务端可校验客户端上报的操作序列是否合法。

## 8. 内容生产管线

### 8.1 当前

策划直接改 `data/*.json`，重启游戏生效。字段见第 4 节。

### 8.2 目标

```
Excel（策划表） → 导出脚本（Python） → JSON → 游戏
```

- 卡牌表列：ID / 名称 / 费用 / 类型 / 稀有度 / 效果1 / 效果2 / 升级后效果 / 描述 / 美术ID；
- 导出时做**静态校验**：ID 唯一、`status` 合法、费用 ≥ 0、描述占位符与数值一致；
- 产物入库，CI 里跑校验，避免「表里改了、游戏没生效」。

### 8.3 复杂卡

不足 5% 的卡需要条件/循环/动态数值（如「每有一张手牌 +1 伤害」）。
为它们预留 `"script": "res://cards/xxx.gd"` 字段，用少量手写效果脚本处理；
**不要**让 95% 的简单卡为此付出复杂度。

## 9. 存档与元进度（设计，未实现）

```json
{
  "version": 1,
  "unlocks": { "characters": ["wanderer"], "cards": ["poison_blade"] },
  "stats": { "runs": 12, "wins": 3, "best_floor": 9 },
  "settings": { "volume": 0.8, "language": "zh_CN" }
```

- 路径：`user://save.json`（Godot 会映射到各平台标准目录）；
- **必须带 `version` 字段**，升级时做迁移函数，否则玩家存档一改就废；
- 局内进度（当前 Run）单独存 `user://run.json`，支持中途退出继续；
- 防作弊：单机游戏不做强校验，但可对存档做简单签名，避免玩家误改导致崩溃。

## 10. 工程规范与质量

### 10.1 测试

`tests/test_battle.gd` 直接实例化 `BattleEngine`，不启动场景：

- 数值类：伤害公式、力量/虚弱/易伤叠加、格挡吸收、中毒结算；
- 流程类：能量不足拒绝出牌、出牌失败不扣费、牌堆洗回、意图推进；
- 鲁棒性：30 个随机种子全自动对战，200 回合内必须分出胜负（防死循环）。

运行：

```bash
Godot --headless --path . --script res://tests/test_battle.gd
```

### 10.2 规范

- 规则层文件一律 `RefCounted`，禁止 `get_tree()`、`await`、`Input`；
- 表现层不修改引擎状态，只调用引擎公开方法；
- 数据字段用小写下划线，中文只出现在 `name/desc`；
- 提交信息：`feat(battle): ...` / `fix(ui): ...` / `data(cards): ...`。

### 10.3 CI（建议）

```yaml
# GitHub Actions 片段
- run: godot --headless --path . --script res://tests/test_battle.gd
- run: python tools/validate_cards.py data/cards.json
```

## 12. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 内容量不足，构筑流派单薄 | 核心乐趣缺失 | 先定 5 个流派原型（毒/力量/格挡反伤/低费快攻/弃牌），每流派 8 张核心卡，再补通用卡 |
| 数值平衡失控 | 某张卡必选或必弃 | 建「自动对战 + 胜率统计」工具，用数据调参而不是拍脑袋 |
| UI 信息过载 | 新手看不懂 | 意图必须直白（数值而非图标）；状态用文字药丸；首次出现给 tooltip |
| 美术风格不统一 | 廉价感 | 先定 1 张基准卡面 + 1 个敌人立绘，全部资源对齐这一张 |
| 移动端适配 | 触控误操作 | 卡牌最小点击区 ≥ 88px；拖拽出牌而非点击；提前在设计分辨率上留安全区 |
| Godot 生态/招人 | 长期维护 | 保持规则层与引擎解耦，必要时可迁移；文档与测试是迁移保险 |

## 13. 已验证结论

1. Godot 4.5 完全胜任该类项目，headless 测试链路顺畅；
2. 规则层与表现层解耦后，**规则可以在 1 秒内跑完全部回归**，迭代速度显著提升；
3. 事件流 + 全量刷新足以支撑卡牌游戏的动画需求，无需引入复杂的状态同步；
4. 数据驱动（JSON）让「加一张卡」变成 1 分钟的事，适合后续大批量内容生产；
5. 中文字体需要在工程内固化，不能依赖系统字体解析。

## 15. v0.2 增量：Web 部署与素材接入

### 15.1 导出配置

`export_presets.cfg` 关键项：

| 配置 | 值 | 原因 |
| --- | --- | --- |
| `variant/thread_support` | `false` | 单线程产物不需要 COOP/COEP 响应头，可直接部署到 GitHub Pages / 对象存储等无法改头的环境 |
| `html/canvas_resize_policy` | `2`（自适应） | 跟随窗口尺寸 |
| `stretch/aspect` | `keep` | 等比缩放 + letterbox，任意窗口比例都不破版（`expand` 会在矮屏裁掉手牌） |

产物（Godot 4.5）：

| 文件 | 大小 |
| --- | --- |
| `index.wasm` | 36 MB（gzip ≈ 9 MB） |
| `index.pck` | 7.6 MB（含中文字体） |
| 其余 | < 350 KB |

### 15.2 部署

纯静态。三种方式（详见 `deploy/README.md`）：静态托管直传 / Nginx / Docker。
唯一硬性要求是 `.wasm` 的 MIME 为 `application/wasm`，以及开启 gzip。

### 15.3 已验证

### 15.4 素材策略（对应 300 卡的美术成本）

300 张卡**不做逐张插画**——那是外包预算的主要消耗项。采用：

```
卡面 = 职业色卡框 + 效果图标 + 标题/数值排版
```

- 卡框：CC0 素材包（Mechanized Magic / Kenney Fantasy UI Borders）或程序化生成；
- 图标：game-icons.net（CC BY 3.0，4239 枚，已挑 31 枚接入）；
- 敌人：DCSS tiles（CC0）或自制剪影；
- 只有 5 张职业主视觉 + 3 张 Boss 需要真正的插画。

这样 300 卡的美术成本可以控制在「几套卡框 + 图标库 + 5 张立绘」的量级。
